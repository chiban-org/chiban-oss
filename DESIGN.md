# Design

Chiban should read as a public record: paper-white surfaces, serif headlines, one pen color. The token values live in `src/features/design/tokens.ts` and are mirrored in `src/app/globals.css`; shared component styles (page rhythm, panels, tables, record lists) live in `src/app/components.css`. Components use token classes (`bg-surface`, `text-ink`, `text-muted-foreground`), never raw hex values.

## Tokens

| Token | Value | Use |
|---|---|---|
| `canvas` | `#f1f5f8` | Page background |
| `surface` | `#ffffff` | Cards, nav, inputs |
| `ink` | `#1f1f1f` | Headings and body text |
| `ink-secondary` | `#2d2f33` | Secondary text, nav, borders |
| `muted` | `#5b6470` | Helper text, metadata |
| `action` | `#2a65a3` | Primary button fill, links, focus ring |
| `highlight` | `#fff7ca` | Attention wash behind a short phrase |
| `status-passed` | `#1e6b3a` on `#e6f4ea` | Passed, approved, issued |
| `status-failed` | `#a3261f` on `#fbe9e7` | Failed, denied, violation |
| `status-overdue` | `#7a4b00` on `#fff7ca` | Past or near a statutory deadline |
| `status-neutral` | `#2d2f33` on `#e8edf1` | Waived, withdrawn, closed, draft |
| `hairline` | `#d5dce3` | Panel, divider and table row borders |
| `control-border` | `#808a95` | Input, select and outline button borders (3:1 on white and canvas) |

`src/features/design/tokens.test.ts` checks every text pair against WCAG AA (4.5:1) and that `globals.css` declares every token.

## Rules

- One filled primary action per screen. Everything else is a ghost button or text link.
- Highlighter yellow marks what needs attention, behind a short phrase, never as a full surface.
- Status is never color alone: use `StatusChip`, which always renders an icon and a text label.
- Records look like documents: serif titles, hairline-bordered white cards on the canvas, almost no shadow.
- A page that refuses the viewer renders `NoPermission`, never a hand-made heading and alert.
- Upload buttons and the submit of any form that is not the page's next step are outline buttons.
- A note that a connection is a practice or stand-in one uses `PracticeNotice`: a dashed outline on white, never a yellow surface.
- Every top-level `<section>` inside `<main>` renders as a hairline panel; nested sections become divided subsections. Add `data-plain` to a section that should not be a panel (an action bar, for example).

## Layout pieces

- `PageHeader` (`src/components/layout/PageHeader.tsx`): kicker, serif title with status chip, lead line, an optional summary, a fact list, and the page's actions. Use it for every record page. On an application the summary is one status sentence (who acts, what, and the deadline due next: "Waiting on: Town (Sam Clerk). Assign a reviewer. Building permit decision deadline: November 13, 2026, 7 days left.") and the stage strip under it. A draft reads "Waiting on the applicant to submit."; a closed, denied, withdrawn or expired record reads only its outcome.
- Stage strip (`src/features/applications/stageStrip.ts`, drawn by `src/components/layout/StageStrip.tsx`): an ordered list of stages built from `CORE_TRANSITIONS` and `STATE_LABELS`. Building permits run Submitted, Complete, Review, Decided, Issued, Inspections, Closed; trade permits skip Complete and, when they issue directly, Review and Decided; board applications run Filed, Accepted, Hearing, Decision, Appeal period. A detour (suspended, or a trade permit sent to review) is inserted as the current stage; an ending other than closed replaces the stages not reached. Done stages carry a check, the current stage a marker and `aria-current="step"`, and every stage keeps its text, so status is never colour alone. The current stage turns the overdue colour, with "(overdue)" beside it, only when a clock or notice deadline is actually late. Progress shows in the strip; the status chip keeps the four status tokens.
- `RecordLayout` (`src/components/layout/RecordLayout.tsx`): a record page body with a sticky right rail. On an application the body leads with the "Do this now" card and the Requirements checklist, then the panels. The rail holds the deadline due next, balance notices, print links while the permit is issued (the permit and placard PDFs serve only issued permits), "More actions" (renewal, the ending moves such as withdraw, deny and close, and "Set step" as a quiet control), the key facts as a stacked `FactList`, and an "On this page" index once there are four or more panels. In windows 1840px and wider the index becomes a left column of the record and sticks there while the page scrolls. Below 1024px a status strip with the deadline and a "Facts and more actions" disclosure replaces the rail above the body; it never repeats the header chip.
- "Do this now" (`doThisNow.tsx`) and Requirements (`requirementsList.tsx`) draw on the shared shells in `src/components/layout/WorkPlan.tsx` (`DoThisNowCard`, `RequirementsPanel`, `RequirementItem`) and both render from `planWork` (`src/features/applications/workPlan.ts`), the one shape of the record's work. The card names the current blocker; when this viewer can clear it, its form is open in the card with the page's one filled button, and other forward moves sit beside it as outline buttons. An ending move in the card is a destructive button, never the filled one. The checklist groups every requirement by stage ("Before review starts", "Before the hearing", "Before the decision", "Before it can be issued", "Before it can be closed"), each row with a check or a cross plus hidden text, its reason, a link to the panel that clears it, its own form in a disclosure, and the override controls. Pages add rows and card warnings through `addRequirement` and `addWarning`, never through new rail props.
- An enforcement case page follows the same pattern from `planCaseWork` (`src/features/enforcement/workPlan.ts`), which reads the case detail and reuses its computed legal state (service gaps per role, answer and judgment appeal dues, the motion gate, the stay). The header summary is one status sentence ("Waiting on: Town (Sam Clerk). Serve Robin Renter. Answer due November 20, 2026, 13 days left."): the town while it has a step, the respondent while an answer period runs, the court after the motion to enforce, town counsel once an answered order is referred, and the Zoning Board of Adjustment while an appeal stays enforcement; the due phrase is the running answer period, then the judgment appeal period, then the corrective action deadline, and none while stayed. A closed case reads "This case is closed." and a case with no violation "No violation was found.", with no card. The stage strip (`src/features/enforcement/stageStrip.ts`) runs Received, Investigating, Violation found, Order issued, In court, Resolved, Closed from `CASE_TRANSITIONS`; stages a resolved case skipped drop out, Stayed is inserted as the current stage after the stage reached, and No violation found replaces the stages not reached. The stay shows only as that stage and as a warning in "Do this now", never as a yellow banner. The card holds the form that clears the step (start the investigation, record a finding, send the notice, record its receipt, draft or issue the order, the role check, recipient or service a gap needs, the next court step, a fine payment, resolve, close) with the page's one filled button; the checklist groups rows under "Before a violation is found", "Before the order is issued", "Before the motion to enforce" or "Before the case is resolved" and links each to its panel. Status moves leave the rail's step card: "More actions" holds Resolve the case as an outline button, Record no violation as a destructive button with a confirmation, and Close the case behind its own disclosure, so the reason field shows only once Close is chosen. Record a finding is offered only in the statuses the server accepts (`mayRecordFinding`), and Record receipt only while a notice has no receipt.
- Enforcement panels go through `arrangePanels` with the stage order from `casePanelPriority` (`src/features/enforcement/panelPriority.ts`): received or investigating, Notes, Complaints, Findings; violation found, Findings, Documents; order issued, Orders, Documents; in court, Orders, Fines, Counsel; resolved or closed, Orders, Documents; no violation, Findings, Notes, Complaints; a stayed case leads with Appeals. Once the order is out, Complaints and Notes fold into "Record and history" unless the stage leads with them. Service shows one `record-item` row per recipient role, and its gaps come from the service status the plan reads: "Not yet checked" only where the status has no check, and the owner agent, which the plan counts as served with the owner of record, reads "Covered by service on the owner of record." (`rolesToServe` and `coveredByOwner` in `serviceStatus.ts` hold the one rule). The service form asks "Server is a" only for hand, abode or summons service and the newspaper only for publication; it and the court step form each carry their own upload ("Upload the proof of service", "Upload the court document"), and the document just uploaded is chosen in the form. A fine payment form sits behind "Record a payment" unless paying is the step. "Show the case on the public site" and "Hide the case from the public site" sit under Visibility in the rail's facts card with their sentence. Answer periods state the rule, the RSA 21:35 counting and the consequence once, then one line per recipient with the service date, the due date and the days left or the answer received. Below 1024px the status strip carries the due phrase and "Facts and more actions" (assignment, facts, parcel, visibility, More actions).
- The case page takes the shape of the viewer (`caseViewFor` in `src/features/enforcement/caseView.ts`). An inspector (the inspector role without the staff role) who records service and is not assigned the case gets the field view (`FieldCase.tsx`): "Do this now", then "Add a photo" and "Add a note" as quick actions, then the service rows of each issued order with their forms, then the other panels read-only, and "Case facts and more actions" folded at the end; there is no rail, no strip and no requirements checklist. The assigned inspector and office staff keep the full page. Someone who refers to counsel but neither manages the case nor records service (the administrator) gets the counsel view (`CounselCase.tsx`): the status sentence, a "Case summary" of findings and orders, Town counsel while an order is in force and no appeal stays it (or once a referral exists), Fines while a judgment allows a fine (or once a fine exists), and every other panel read-only inside a closed "Record and history". Capability checks stay on the server for every view.
- Board meetings and deadlines (`src/features/applications/meetingDeadline.ts`): the deadline a board meeting must meet is the open clock its vote meets, read from the record's clocks (the completeness determination for the Planning Board, the hearing deadline for the ZBA). Every meeting picker (the board panel's and the hearing scheduler's) marks each meeting "meets the deadline" or "after the deadline", "filed too late for this meeting" when the filing lead rules it out, or "too soon to mail notice" when today is past the earliest due date of the notices the application needs for that meeting (worked out by the same notice requirements and town lead settings as the notice checklist: the Planning Board mailed notice, the ZBA mailed and newspaper notice, and the 14-day certified regional notice when regional impact is yes or not yet determined). A meeting with a scheduled hearing counts as noticeable while every one of its notice items is either proved on time or still before its due date, confirmed or not. This holds for any open application; the filing lead applies only before acceptance. The board panel picker repeats the chosen meeting's mark as a hint under it, since a phone cuts off the end of a closed select. When the meeting set is after it, "Do this now" warns ("The meeting set, November 25, 2026, is after this deadline: ...") and, for a viewer who can set meetings, holds the move form with the latest meeting that meets the deadline, was filed in time and can still be noticed chosen, and "Move the meeting" as the filled button; with no such meeting the warning says why and the vote stays the step. Accepting the application is offered only once the meeting has happened and every requirement before the hearing is met; until those requirements are met the board panel offers only "Record that the board did not accept it".
- The meeting date shows once, in the board panel's acceptance or hearing section, which also holds the picker. The checklist row is only its check. Until a hearing record exists, a ZBA application's Hearings panel points to that section instead of saying no hearing is scheduled; once records exist the board panel points to the Hearings panel instead of listing them.
- The record page takes the shape of what the viewer can do on it (`recordViewFor` in `src/features/applications/recordView.ts`). Someone who records inspections but neither manages the workflow nor issues permits gets the inspection view (`inspectorRecord.tsx`) on an issued permit or any record with inspections; before issuance they keep the full page. The status sentence names the inspector and the next inspection ("Waiting on: Inspector (you). Framing reinspection today at 10:30 AM."). The next scheduled inspection leads, an owed result first, with its checklist open and Record result as the page's one filled button; then the last result with its notes and photos, the open inspection requests, conditions, documents and any staff notes, read-only. Fees, reviewers, clocks, code edition, regional impact, the requirements checklist and More actions are left off. Print permit, print placard, the deadline, key facts and parties fold under "Permit facts" at the end. Reviewers and board members keep `LimitedRecord`: a reviewer's status sentence and rail card give the comment due date ("Waiting on: Reviewer (you). Comments due November 18, 2026."), "Open your review" is the filled button while the review is open, and the body shows the project summary from the form answers (staff-only questions left out) and the plan documents.
- `arrangePanels` (`src/components/layout/splitPanels.ts`): a panel counts as empty when nothing is on file, whatever the viewer can add. Empty panels collect at the end under "Nothing recorded yet" as one-line rows, with any add action as a disclosure on the right. Filled panels lead in the stage's order from `panelPriority` (`src/features/applications/panelPriority.ts`: in review, Reviewers, Completeness, Clocks, Fees; a board application before its decision, Board, Hearings, Clocks; decided, Conditions, Fees, Code edition, Regional impact; issued, Inspections, Conditions, Fees, Appeals; ended, Documents, Inspections), then the rest in their usual order. Recent activity, Records and Parties fold into a closed "Record and history" disclosure unless the stage leads with them. `splitPanels` keeps the plain filled and empty split for other record pages.
- Each document row carries one "Who can see this" block (`src/components/documents/WhoCanSee.tsx`): a sentence computed by `whoCanSeeSentence` (`src/features/documents/whoCanSee.ts`) that names who can open it and whether it is on the public site and why not ("Town staff and project parties. Not on the public site: no copy is approved for the public yet."), shown to every viewer, then the controls behind "Change who can see this": signed-in access, Show on the public site, approval, revocation and the redacted upload, one form per action so each keeps its own capability. The row's chip reads "Shown on the public site" or "Not on the public site" from the same `publicStateOf`, so chip and sentence agree with `publicDocument` in `visibility.ts`. "See what the public sees" opens the public parcel page in a new tab, on the row of a shown document with a parcel and in the header of the staff application (past draft), the public enforcement case with a parcel, and the staff parcel page.
- On a record page each form appears once. A form the card or the checklist holds is dropped from its panel; other forms that add something (assign, apply, record, refer) sit behind a `<details>` disclosure named for the action. Ended records offer no add forms beyond records work (holds, building removal, documents). List pages follow "Lists and filters" instead.
- Lists of records inside a panel use `record-item` dividers, never bordered boxes inside a bordered panel. A list that would stand alone on the page goes in a panel with a heading first.
- Top-level blocks inside `<main>` sit 20px apart and the lead line sits 4px under the `h1`, both from `components.css`. Pages do not add `space-y-*` to `<main>`, margins to its direct children, or classes to the lead line.
- A page below another one (an import run under Imports, a user under Users) names its parent as a link in the kicker above the title, through `PageHeader` or `SettingsHeader`'s back link.
- Data tables sit in a `table-panel`; filter bars above them in a `toolbar`. Tables never add their own row border or cell padding classes; the base table style draws them. Status columns use `StatusChip`, in panels too, and empty cells read in muted text.
- Staff navigation lives on its own `sidebar` layer (`#e9eef2`), a step darker than the canvas. Entries are grouped by the `group` field in `src/features/staffNav/navItems.ts` and each carries an icon. The current page is a white row with a hairline edge.
- Records and reports and Parcel data fold away unless the current page is inside them. Configuration and administration pages sit behind one Settings entry, shown to anyone who can open at least one settings page.
- Parcel data shows only to those who can manage parcels or run imports. Data export (under Records and reports), Move open applications over and Scanned property files (under Parcel data) sit in the main nav for those who can open them without editing configuration; configuration editors find them in the Settings menu's Administration group instead. An entry with a `parent` (My day under Inspections) is indented beneath it when both are visible.
- The person's name, role, Account and Sign out are pinned to the bottom of the sidebar; only the entries scroll.
- A search field, "Find a permit, case or parcel", sits under the town name at the top of the sidebar and in the phone top bar (`RecordSearch` in `src/components/staff/search`). Typing an exact record number (an application or permit, an enforcement case, a cease and desist order or complaint, a Right-to-Know request, a receipt) and pressing Enter opens that record. Otherwise, after a short pause, it lists up to five matches per group: Applications (number, type, address, status chip), Enforcement cases, Parcels (ID, address, owner) and Requests, moved with the arrow keys and Enter and closed with Escape. A number search adds "See all application matches", which opens the Applications list with the search applied. The server (`search.find`, staff only) applies each target page's own access rule, so a viewer only ever sees records they can open and no counts. In the icon rail it is a search icon that expands the sidebar. It has no keyboard shortcut.
- The sidebar collapses to an icon rail with tooltips. The choice is kept in the `chiban_staff_nav` cookie so the server renders the right width. Below 768px it becomes a top bar and a drawer.
- The staff home (`/staff`) is a start page per role under a parcel search (`src/features/staffHome`): a clerk or planner sees what is waiting on them, the next deadlines and the counter; an inspector, results still owed, today's route, requests to schedule, their open cases and the next inspection days; finance, payment problems, fees, today's receipts with the cash report, and overpayments to refund; a records custodian, Right-to-Know requests by statutory day, preservation retries, disposition batches, holds and exports; admin, system health, users, settings drafts not yet in use, and imports and exports. Someone with several roles sees a panel for each, most urgent first. Each row is a count linked to the full list; a panel with nothing to count says "Nothing waiting." Reviewers land on their reviews and board members on `/board`.
- `/board` puts the next meeting and its packet first, then later meetings, then earlier ones.
- The theme is light only. Tailwind's `dark:` variant is bound to a `.dark` class that nothing sets, so an operating system dark setting cannot restyle controls.

- A rail taller than the window scrolls with the page instead of sticking, so its bottom is never cut off.
- In long lists on a record page, urgent items (the deadline due next, anything late) stay open and the rest fold to one line.

## Settings

- Settings and administration pages (`/staff/settings/*` and `/staff/admin/*`) share one shell: a settings menu about 15rem wide on the left inside the content area, and one focused page on the right. The menu model lives in `src/features/settingsMenu/settingsMenu.ts`, grouped (Town, Permits, Town rules, Boards, Money and inspections, Starters, Administration); add a page by adding an item there.
- The menu lists only the pages the viewer can open, using each page's own access rule, and marks the current page like the main sidebar's current row. Each group is a heading with an icon and a count that opens and closes; only the group holding the current page starts open, so the menu never reads as one long list. A filter box at the top narrows it and opens every group with a match. Below 768px it becomes a picker at the top of the page.
- `/staff/settings` opens the first page the viewer can use. A viewer who can open none gets the permission refusal.
- One page per setting, never a long hub. Every page starts with `SettingsHeader` (`src/components/settings/SettingsHeader.tsx`): the title, one plain line saying what the page controls, and the page's one filled action on the right (New type, Request a new export) where there is one. The versioning sentence joins that line only on kinds that open applications pin (application types, forms, fee schedules, templates, conditions, checklists).
- Kinds that hold one record (payment, inspection and board settings, regional notice contacts, review committee routes) open straight to their form and version history instead of a one-row list.
- The Town group (Town profile, Letterhead, Signers) edits one town profile. Each page puts its part into use straight away as a new version, with no draft step, and links to the version history on the town profile kind page. The Letterhead page shows a live preview of the header and footer next to its form.
- An empty kind shows what it does and the add action in its place, never a bare 0.
- Settings pages are not record pages: no `RecordLayout`, and `main[data-wide]` only when a table needs the width.
- Settings editors speak in the town's terms. Items are listed, titled and picked by name; keys, codes, inspection types and fee formulas as data sit under a closed "Advanced" disclosure. A new item starts from a name, and its short name is made from it (`src/features/config/newItemKey.ts`).
- The shared pieces live in `src/components/config/plainFields.tsx`: `NamePicker` and `CheckedNames` pick other configuration by name and store its key, `TextRows` edits a list one row per entry, `DollarsInput` and `PercentInput` show dollars and percent while storing cents and basis points. A choice list longer than ten folds behind "Choose from all N" under a "Chosen:" line.
- Every field has a plain label, and a one-line hint when its meaning or unit is not obvious. Field grids are one column below 640px.
- A required field carries a red asterisk after its label (`RequiredMark` in `src/components/ui/required-mark.tsx`, `aria-hidden`, so the native `required` attribute is what screen readers announce). `Field` and every wrapper built on it (`TextField`, `AreaField`, `SelectField`, `CheckField`, `DollarsInput`, `PercentInput`, `NamePicker`, `CheckedNames`, the address and parcel pickers) take `required` and draw the mark; a form that builds its own `Label` renders `RequiredMark` inside it, and `FormRenderer` marks a field exactly when it is required at that moment, including `requireIf`. Every form (`ActionForm` and the hand-made ones) opens with `RequiredNote`, a muted "* Required" line that stays hidden unless the form holds a required control. `src/requiredFieldMarks.test.ts` scans hand-made labels.
- Field grids align to the top: `Field` is `content-start`, so a neighbour with a longer hint never pushes a label or input down. Rows of fields never use `items-end`.
- A button that acts on one input (Remove, Move up, Preview) is that field's `action`: it sits right beside the input, between the label and the hint, at the input's height (`RowButton` is the default button size, `h-9`). It never floats to the far edge of the row, and beside a textarea it lines up with the textarea's top.
- A checkbox lines up with the first line of its label (`CheckLine`), however many lines the label runs to.
- Each fee shows a worked example in a sentence ("For Finished area of 1,200 ..., this fee is $420.00."), worked out by the same calculation that charges applicants.
- `PublishBar` explains Save draft and Put into use once, above the buttons. Put into use and Restore open a confirmation that says what changes: open applications keep their version on kinds they pin, everything else takes effect at once.

## Lists and filters

- One list per kind of record. Status or scope is a row of `FilterTabs` with counts above the filter bar, not a second page. Tabs pick one value, and "Clear all" leaves the chosen tab alone.
- Tabs always sit under the lead line and always use `FilterTabs`, including tabs that switch between sibling lists (the three override lists).
- A list's Add action sits at the top, never only after the last row. The page header carries it: `ListHeader` (`src/components/layout/ListHeader.tsx`) on list pages, `SettingsHeader`'s action on settings pages, and `SectionHeader` beside the heading when the list is one section of a page (the three notice contact lists). Add is the page's one filled button unless the page already has one; then it is outline.
- Add opens its form in `FormDialog` (`src/components/FormDialog.tsx`), titled for the action, with an outline submit. A form too long for a dialog sits in a disclosure directly under the header instead. A dialog closes with Escape or its close button and scrolls inside itself on a short window.
- Every row that can be corrected has an Edit action: `RowEditDialog` opens the same form filled in with what is on file and saves through an update action. The update checks the same capability as the create action, keeps the server's own validation, and writes an audit entry with the values before and after. Rows that open their own record page (a request, a case, a meeting) take no Edit in the list; whatever that record allows changing is on its page.
- When rows are unique by a key (a roster per parcel), Add refuses a key that is already listed and the message points to that row's Edit. Edit shows the key as text and does not change it.
- Row actions sit in the last column under a screen-reader-only "Actions" header: Edit first, then any destructive action with its confirmation. Edit's accessible name names the row ("Edit Avery Stone").
- A list that can grow past about 25 rows shows 25 at a time with `TablePager` under the table (requests, cases, meetings, legal holds, board members, the three override lists). Lists that stay short (notice contacts, enforcement officers, export targets) do not page.
- A table's download link reads "Download CSV" and is hidden in print.
- List pages use `<main data-wide>` so the table can use the wider list width. The lead line states the default order.
- Every meaningful column sorts from its header with `SortHeader`, one sort link per header. Paged or growing lists sort and filter in SQL with a stable tiebreak and page with `limit` and `offset`. Lists already sorted and filtered in memory (the override lists) page after sorting with `slicePage` from `src/features/dataTable/pageSlice.ts`. Narrow layouts get the same sorts through `SortBar`.
- The enforcement case list (`/staff/enforcement`) follows this section. Its status tabs (Open by default, Order issued, In court, Closed, All) are `FilterTabs` over the `stage` parameter, with counts from the status facet; Overdue and Due this week stay quick filters. "Next step" and "Due" come from `planCaseWork`, the same plan the case page reads, so the list and the case page never disagree: Next step is who acts and the task ("Town: draft a cease and desist order", "Respondent: answer the order", "ZBA: decide the appeal", "Court: rule on the motion to enforce"), Due is the plan's due date with its label and days left ("Answer due, 13 days left"), muted "None" when the plan has none (a closed, stayed or not yet ordered case), and a date already past is marked in text as "N days overdue" besides the attention colour. `loadCaseDueIndex` (`caseDueIndex.ts`) loads the plan inputs for every visible case in order issued or in court in batched queries (`loadCasePlanInputs`, `staysFor`, `fineDueByIds`), and the Overdue (due date before today), Due this week and No deadline filters, their counts and the Due sort all read that index, so they cannot drift from the shown date; only Due sorts, and cases with none sort last either way. Below 768px rows become cards with the case number on one line (never wrapped), Next step directly under it and the sort links in `SortBar`. On this page "Enter a complaint" is the filled button and "Open a case" the outline one,; the complaint dialog also takes the complainant's name, phone and email, kept on the complaint and shown only on the case page to staff who manage enforcement, and saving opens the case the complaint created.
- Quick filters come from `chipGroups` in `src/features/dataTable/quickFilters.ts`: two to four groups, counts from `countFacets`. Options that exclude each other (Mine and Unassigned, Overdue and Due this week) set `single: true` and are read with `singleValue`. Groups longer than three options, and anything not every viewer needs, go behind a `FilterMenu`.
- Below 640px every filter group folds into a menu. No staff page scrolls sideways at 390px.
- Identifiers link to their record: an application number to the application, a parcel ID to the parcel, an owner to a parcel search for that owner. An identifier gets its own column instead of sitting inside a sentence.
- A field that asks for a parcel is the parcel picker (`ParcelPicker` and `ParcelMultiPicker` in `src/components/parcels/picker`), never a bare text box. It searches address, owner and every form of parcel ID after a short pause, lists up to eight matches with the display ID, site address and owner, labels retired parcels, and moves with the arrow keys, Enter and Escape. The choice shows as a chip with Change, and the form submits the parcel's record id under the field's usual name. Where a form may name a parcel that is not in the layer yet (lineage children), "No parcel matches" comes with "Use this ID anyway", which submits the typed ID.
- No custom keyboard shortcuts. Standard browser keyboard use only: Tab order, visible focus, Enter and Space on links and buttons, Escape to close dialogs and menus, arrow keys inside listboxes and selects.
- Search forms offer recent searches and a one-click example under the field.
- A list of people inside one record (association officers, park tenants) is edited as repeatable rows: one bordered group per person with its own fields, "Add another" under the last one and Remove on each when there is more than one. Never a delimited text box.
- Rows that can go out of date carry a checked date. "Confirm still correct" records today without retyping anything; past the town's re-check interval the row shows a "Due for a check" chip and the page header counts what is due. Due is a warning, never a block.
- A row that other records use says so in a "Used by" column ("Used on 2 lists"), which opens to each use with its number and status, linked. A row that keeps history opens "Earlier versions" in a dialog, newest first, each with who replaced it and when.

## Notice contacts

- `/staff/notice-contacts` (formerly Rosters) keeps the people mailed notice instead of, or as well as, the parcel owner: condo associations, manufactured housing parks, conservation and preservation restriction holders, and a read-only view of the regional and state contacts kept in Settings. Each section opens with one plain line saying when its people are notified. Tables show full mailing addresses.
- Each row has Edit, Confirm still correct, Earlier versions and Used by. Restriction holders also have End, which asks for a date and confirms; Undo stays until a list issued after the ending has left the holder off. The land records check ("Land records checked for new restrictions on ...", with Record a check) is the only review kept for a whole section, because a list cannot be issued until it has been done once.
- The re-check interval is stored in the board settings (365 days by default) but is changed on the Notice contacts page, beside the due count, by anyone who can edit settings; saving puts a new board settings version into use with only that value changed. Past it the row shows Due for a check and abutter lists print its source as out of date; they still issue.
- Multi-unit parcels with no association on file are listed under the condo section, each with Add association already filled in with the parcel. The abutter list links its missing-association reason to the same prefilled Add, and links every notice contact source back to its row.
- A parcel page shows a "Notice goes to" panel with that parcel's officers, park owner and tenants, or restriction holders, each with Edit.

## Actions and roles

- An action appears only when the viewer can take it and it applies in the record's current state. A finished application shows no board, review or abutter actions; money, records and legal-deadline work stays available.
- The server refuses the same action on the same grounds. Hiding a button is never the only check.
- The staff menu lists only pages the viewer can open. A viewer with no list to work from lands on a page they can use, never on a bare permission refusal.
- Reviewers and board members see read-only versions of records, without buttons they cannot use.
- Every destructive action asks first in one shared dialog, `ConfirmDialog` (`src/components/ConfirmDialog.tsx`). Destructive means it deletes, removes, cancels, voids, withdraws, revokes, disables, dismisses, ends, denies, closes, rejects, unpublishes, resets, restores an older version over a newer one, or records an outcome that cannot be taken back (a payment outcome by hand, a refund, a returned check, a board decision). A form opts in with `ActionForm`'s `confirm` prop; `when` limits it to the choices that destroy (closing a case, unticking Show on the public site).
- The dialog's title names the record and the action ("Cancel the November 20, 2026 Zoning Board meeting?") and its one line says what changes, in plain words. Cancel sits on the left and takes focus; the confirm button on the right names the action again and is destructive, except for putting a setting into use, showing something on the public site and recording a board vote or decision. A required reason is checked before the dialog opens, Escape and Cancel send nothing, and the server keeps its own checks. `src/components/destructiveActions.test.ts` fails when a form with a destructive label or action has no `confirm`.
- Removing a row or block inside a settings editor changes only the unsaved draft and does not ask; Put into use asks.
- An issued permit, or one that closed when it was issued, is corrected in place through "Correct this permit" in the record rail, shown only to staff who hold both `application.amend_after_review` and `permit.issue`. A correction changes the contractor (picked from the project's parties or added) and license number, the form answers and the project title, and needs a reason. It keeps the permit number and reissues the permit as the next revision: a correction snapshot, a `permit.correct` audit entry with the reason, the revision and the values before and after, and a new stored permit copy. The earlier copy stays on file marked superseded; the portal lists it under the current copy as an earlier version. Print permit, Print placard and the stored copy show "Corrected, revision N, <date>" under the title.
- The correction dialog checks the fees on the corrected answers as staff type ("No fee changes") and lists who will be notified: every party with an account, and a replaced contractor. A change to an answer that decides the review, or one that would change any fee, is refused with a pointer to an amended application, and so is changing the permit type, the parcel or the board's conditions, which the dialog does not offer. Saving asks first ("Reissue permit <number> as revision N?").

## Builders

Builders let town staff shape configuration without knowing how it is stored. The form builder (`src/components/config/formBuilder`) and the letter builder (`src/components/config/letterBuilder`) follow the same rules.

- Three panes: what can be added on the left, the thing being built in the middle as its reader will see it, and the settings of the selected part on the right. In narrow windows the panes stack, and selecting a part scrolls its settings into view.
- Plain-language names everywhere: question types are Short answer, Paragraph, Whole number, Number, Money, Date, Dropdown, Checkboxes, Yes / No, Email, Phone and Section. Rules read "Show only when" and "Required only when" and are built from three dropdowns (question, test, answer). Storage details (the key, the fact, staff only) sit under a closed "Advanced" disclosure.
- Keys are made from the text a person types and stop changing once a version in use has used them.
- Reorder by dragging a handle, by keyboard on the same handle (space, arrows, space), or with Move up and Move down.
- Removing something that other configuration uses opens a warning that names each use before anything changes.
- "Preview as applicant" shows the real form at desktop and phone width, fillable, with the same validation messages applicants see.

The letter builder edits templates on a letter-sized page under the town letterhead:

- The Insert pane holds blocks (Signature, Conditions list, Field table, Notice box), the parts filled in from the record for that kind of document, and merge fields grouped and named in plain words. Insert and toolbar buttons never take focus from the letter.
- Merge fields are highlighted chips with their plain name. "Preview" with a real record of the right kind swaps every chip and record part for that record's values; "Download PDF" renders exactly what would be sent.
- Wording state law requires is a locked block: a lock icon, the reason ("Required by state law"), and no way to edit or delete it.
- In settings-menu width the Insert pane and the selected part's settings share the left column; wide windows get three columns.

## Board packets

A meeting's packet is prepared, sent and tracked in one "Packet" panel on the meeting page (`/staff/boards/meetings/[meetingId]#packet`). `/staff/boards/packets` is a read-only list of upcoming meetings with each packet's state and a link to that panel. Older packets that belong to no meeting are listed under it, each on its own page where its private links can still be turned off.

- The panel opens with one state line: "Show the agenda on the public site to start the packet", "Not sent yet", "Sent to N members on <date>", "N changes not sent yet" or "Meeting cancelled. Packet closed." (`src/features/boards/packetState.ts`). The same line is the Packet fact in the rail and the chip on the packets list. While the packet is unsent or has changes not sent, the rail's next step is a link to the panel ("Prepare the packet" or "Send the packet update").
- Four steps in order: Gather, Review, Send, Track.
- Gather lists candidates grouped by agenda item, plus anything already in the packet that is no longer on the agenda, with a checkbox each. A document that cannot go in stays in its group with the reason in plain words ("Not shared with the board", "Belongs to the ZBA", "No approved public copy"); "Not shared with the board" carries a Share with the board button for viewers who can manage documents. Each application offers "Make TRC summary" (or, once one exists, an unchecked "Make a new TRC summary") or says "No TRC review on this application". Viewing creates nothing; only Save does.
- Review shows the contents in order with a cover page preview and the title, prefilled "<Board> packet, <date>". When the agenda is shown on the public site again it asks "The agenda changed. Replace it in the packet?"
- Send offers "Send to the <board> (N members)" from current membership, and "Also send to someone outside the board" behind a disclosure, which sends a private link with an expiry. Each recipient row says in words what they get ("signs in on the board page" or "private link, expires <date>") with Resend, and Turn off link for private links, which asks first.
- After sending, the packet stays editable. Additions, removals and replacements are held as changes not sent, marked beside each item in Review, until Send update emails only what changed ("Added: ...; Replaced: ...").
- Track is a table per recipient: sent, first opened, last opened, documents opened.
- Cancelling a meeting turns off its packet's private links, and the cancel form asks whether to email the packet's recipients.
- Members see a packet on `/board` only once it is sent: "New" until they open it, "Updated <date>" after an update they have not opened, and the meeting marked Cancelled instead of disappearing. The packet page starts with the cover page, marks items Added or Replaced, and keeps withdrawn or removed items in the list with the reason.

## Links

- Links inside page content are underlined, from one rule in `components.css`. Links in table cells stay plain until hovered. Navigation, tabs, sort headers, chips and buttons are never underlined.
- Pages do not add color or underline classes to links; a link that must not underline opts out with `no-underline`.

## Copy

- Plain words, no internal jargon, and no text repeated within one panel (a gate's label and its reason, for example).
- A count appears only when it says something: "2 more overdue", never "0 overdue".
- An empty state says what to do next.
- A count of days reads "today" when it is zero.
- Dates read in full ("November 4, 2026") through `formatCivilDate`. Only the two work queues (Applications and Your reviews) and the parcel page's Records table use the short month, to keep their many columns on one line.

## Type and shape

- `h1` and `h2` use `Charter, "Source Serif 4 Variable", serif` (22px and up). `h3` and `h4` use the body face in bold.
- Everything else uses Mulish Variable at `-0.02em` tracking. Fonts are self-hosted through `@fontsource-variable`.
- Scale is Major Second (1.125) from a 16px base.
- 4px spacing base, 10px radius, 24px card padding, 1200px maximum content width.
- Staff pages start at the same distance from the sidebar on every page. Content aligns left beside the sidebar and is never centered, so wider windows add space on the right only.

## Hierarchy and rhythm

Every panel reads in the same order: heading, lead, content. The spacing lives in `components.css`, so pages never set it themselves.

- A panel's heading and lead come from `SectionHeader` (`src/components/layout/ListHeader.tsx`): the `h2`, an optional action on the right, and an optional `lead` 4px under the heading in muted text, no wider than 75ch. Use the lead for the one line that says what the panel is for or what policy applies ("A document shows on the public site only while the case is public ..."). Content starts 16px under the header.
- Blocks inside a panel sit 12px apart. A subsection inside a panel is an `h3` (body face, bold): 24px above it, 8px between it and what it heads. A label that names a group of rows ("Regional planning commission") is a subsection heading or a description list label, never plain text the same size and weight as the rows.
- Panels (`<section>` in `<main>` without `data-plain`) never carry `space-y-*`, and their direct children never carry `m-0`. Inside any `space-y-*` container, direct children never carry `m-0` either: in Tailwind 4 `m-0` cancels the `space-y` gap, which is what jammed headings against their text. `src/sectionRhythm.test.ts` scans every source file for both. Shared components do not put `m-0` on their root element for the same reason; preflight already zeroes `p`, `ul` and heading margins.
- Label and value pairs use `DescriptionList` (`src/components/ui/description-list.tsx`): muted semibold labels in a fixed column (`narrow` 8rem, `default` 11rem, `wide` 14rem), values beside them, 12px between rows, and label above value below 640px. A value that is several items (municipalities, conditions) is a list inside the value, never items joined with semicolons. Only the letter builder's page preview keeps its own `dl`.
- Key facts for a whole list page (a due count, an interval with its Change button, and the footnote that explains them) sit together in `KeyFacts` (`src/components/layout/KeyFacts.tsx`) directly under the header: a white strip with the facts on one line and the footnote in muted small text under them. Full-sentence statements (Anonymous intake's status) use `stacked`, one per line. Facts about one record stay in `PageHeader` or the rail's stacked `FactList`.
- A group of related fields is a `<fieldset>` named by `Legend` (`src/components/ui/legend.tsx`): 16px semibold ink, one step above a field label (14px medium). `bordered` puts it on the border of a boxed group (`FieldGroup`, the board and inspection settings); plain groups (Mailing address, Contact details, one signer) put it 12px above the first field and sit 32px from the next group. A legend that asks one question over radios or checkboxes ("Method", "Roles") is that question's label and keeps the field label style.
- A list of records inside a panel uses `record-item` rows; each row reads as one unit: its title line, then its muted metadata 4px under it, then its disclosure. The panel's policy text belongs in the lead, not between the rows.
- A row with more than one action stacks them in `row-actions`: one column, Edit on top, every button the width of the widest. Actions never wrap halfway across a row. Tables that are still too wide scroll inside their `table-panel`; the staff content column has `min-w-0` so a table never widens the page.
- A long reference list that groups items under names (the state law rules by classification) is one row per name with its count ("8 required rules"), opening to the items as a list. An empty group says so ("No required rules") and does not open.

## Two densities

- Public shell (`.public-shell`): 16px minimum body text, 44px minimum tap targets, single-column forms, mobile first.
- Staff shell (`.staff-shell`): denser tables, 14px allowed in tables only.

- Two phrases keep visibility and use apart in staff copy. "Show on the public site" (with "Hide from the public site", "Shown on the public site", "Not on the public site") means signed-out visitors can see it, and the control says which public page: an agenda shows on the board page and the meetings page, a migration batch and an uploaded parcel file on the parcel's public page, an enforcement case on the parcel's public page. "Put into use" (with "In use", "Not in use yet") is for settings and config versions, which never become public. The word Publish stays only in capability keys, audit actions and database values. A staff application, and an inspection that is scheduled, passed or failed, carries one quiet line saying the public parcel page lists it with its number, type, status and dates.
